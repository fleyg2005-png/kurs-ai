Коммиты, ветки, pull request — на симуляторе

Самая «программистская» часть курса. Разберём её на учебном симуляторе, где ничего нельзя сломать, а потом повторим в настоящем GitHub. После этого урока вы будете понимать, что именно делает ИИ-агент, когда «открывает PR».

Зачем нужны ветки

Представьте чистовик документа, который уже отправлен клиенту, и черновик, в котором вы пробуете новую редакцию раздела. Черновик можно испортить, бросить, переписать три раза — чистовик не пострадает. Когда редакция готова, вы переносите её в чистовик. В git это выглядит так:

  • main — чистовик. Именно его публикует GitHub Pages, именно его видят все.
  • Ветка — черновик. Копия main на момент создания. Всё, что вы коммитите в ветку, в main не попадает.
  • Pull request (PR) — записка «посмотри и утверди». К ней прилагается diff — точный список того, что изменится.
  • Merge — перенос в чистовик. После него main содержит изменения, а сайт обновляется.
main→ ветка→ коммиты→ pull request→ проверка→ merge в main→ сайт обновился

Зачем это не-программисту? Потому что ИИ-агенты работают только так: каждая задача — своя ветка и свой pull request. Вы не разбираете их код построчно, вы смотрите diff, проверяете результат и нажимаете Merge. Или не нажимаете. В этом и есть контроль.

Симулятор

Слева — файл и кнопка коммита, справа — история. Жёлтая полоска сверху ведёт по заданиям: выполняйте их по порядку. Это учебная модель, в ней нет ни GitHub, ни интернета — только логика git.

Обратите внимание на историю после merge: коммиты из ветки появились в main, плюс добавился коммит «Merge pull request». Ветка больше не нужна — её история никуда не делась.

То же самое в настоящем GitHub

Названия кнопок — как на экране. Делать это прямо сейчас не обязательно: в разделе «Практика» будет задание.

  1. Создать ветку. В репозитории над списком файлов есть кнопка с названием текущей ветки — main ▾. Нажмите её, введите имя новой ветки (например, update-list) и нажмите Create branch update-list from main. Теперь вы «внутри» ветки — её имя написано на кнопке.

    🌿 main ▾1Add file ▾Code ▾
    update-list

    ＋ Create branch update-list from main

  2. Сделать коммит в ветку. Откройте файл, нажмите карандаш, внесите изменение, нажмите Commit changes…. В окне проверьте: коммит идёт в ветку update-list, а не в main. Напишите сообщение, нажмите Commit changes.

    Короткий путь. Если вы редактируете файл прямо в main, в окне коммита есть переключатель Create a new branch for this commit and start a pull request. GitHub создаст ветку и сразу откроет форму PR.

  3. Открыть pull request. Вернитесь на главную страницу репозитория: GitHub покажет жёлтую плашку с кнопкой Compare & pull request. Нажмите, проверьте направление (update-list → main), напишите заголовок и пару слов о том, что и зачем изменили, нажмите Create pull request.

    Open a pull request

    base: main ← compare: update-list · ✓ Able to merge

    Добавить раздел «Контакты» на главную
    Create pull request

  4. Проверить diff. Во вкладке Files changed зелёным показаны добавленные строки, красным — удалённые. Наведите на строку и нажмите «+» — можно оставить комментарий прямо к ней. Так вы будете общаться с ИИ-агентами.

  5. Слить. Во вкладке Conversation нажмите Merge pull request, затем Confirm merge. Появится кнопка Delete branch — нажмите, ветка больше не нужна. Через несколько минут изменения появятся на сайте.

Три правила, которые избавят от проблем

  • Одна задача — одна ветка. Не «ветка-на-всё», а fix-header, add-calculator, update-contacts. Маленькие PR легко проверять и легко откатывать.
  • В main — только через PR. Даже если вы один. Привычка смотреть diff перед merge — та самая, которая спасёт, когда diff будет написан агентом.
  • Слили — удалили ветку. История сохранится в коммитах, а список веток не превратится в свалку.

Проверьте себя

Вы сделали три коммита в ветке add-calculator. Что видят посетители вашего сайта на GitHub Pages?

  • Новую версию с калькулятором
  • Старую версию: сайт собирается из main, а в main ещё ничего не слито
  • Ошибку, пока PR не закрыт

Ветка не влияет на main, пока вы не сделаете merge. Это и есть смысл веток: можно работать, ничего не ломая.

Что такое pull request?

  • Команда скачать репозиторий на компьютер
  • Предложение влить изменения из ветки в main, с diff и обсуждением
  • Запрос на доступ к чужому репозиторию

PR — это «посмотри и утверди». Пока его не слили, в main ничего не меняется.

После merge вы удалили ветку. Что стало с её коммитами?

  • Удалились вместе с веткой
  • Остались в истории main — ветка была лишь указателем на них
  • Переместились в архив GitHub на 30 дней

Merge переносит коммиты в main. Имя ветки после этого — просто ярлык, который можно убрать.

Почему ИИ-агент всегда работает в отдельной ветке и открывает PR, а не пишет сразу в main?

  • Потому что у него нет прав на main
  • Чтобы вы могли проверить diff и решить, принимать изменения или нет
  • Потому что main нельзя редактировать в браузере

PR от агента — это контрольная точка. Никакие изменения не попадут на сайт, пока вы не нажмёте Merge.

Практика

Повторите цикл в своём репозитории hello-ai (или в том, что создали в контрольной 4).

  • Создана ветка с осмысленным именем, в ней — минимум один коммит.
  • Открыт pull request с заголовком и описанием; во вкладке Files changed я посмотрел(а) diff.
  • Оставлен хотя бы один комментарий к строке в diff.
  • PR слит (Merge pull request → Confirm merge), ветка удалена.
  • Через несколько минут изменение видно на сайте.

Вы умеете то, что отличает «пользуюсь GitHub» от «работаю с GitHub». Следующий урок — что делать, когда что-то пошло не так, и почему это почти всегда поправимо.
