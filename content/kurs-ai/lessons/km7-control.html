Финальная контрольная: ваш инструмент в работе

Без степперов, подсказок и готовых ТЗ: сделайте сами второй инструмент для своей маркетинговой работы — не тот, что в модуле 6. Вы одновременно заказчик, проверяющий и приёмщик; git, как и раньше, делает агент. Закладывайте около часа без учёта ожидания агента.

Задание

  1. Выберите инструмент — другой, чем проверка постов по чеклисту (идеи — в таблице урока 23). Убедитесь вопросом из урока 23, что ему не нужно работать без вашего сообщения агенту и хранить данные от нескольких людей.
  2. Создайте новый приватный репозиторий с README и загрузите в него 3–5 своих рабочих файлов без персональных данных — посты, письма, выгрузки, шаблоны — через Add file → Upload files. Дайте агенту доступ: установите Claude GitHub App на этот репозиторий.
  3. Первым запросом в новой сессии (новый репозиторий, main, окружение full, режим Auto) попросите агента создать AGENTS.md и CLAUDE.md: возьмите блок «Правила» из первого запроса урока 14, пункты 1–5 подгоните под свои файлы, раздел «Как сохранять работу» оставьте дословно. Обязательно со строкой «Ветки и pull request создавай сам и сразу сливай в main — я на GitHub ничего не нажимаю».
  4. Напишите ТЗ по шаблону урока 23 своими словами: что есть, что сделать (программа, запуск, результат в репозитории, README), ограничения, критерии готовности с проверяемым примером по конкретному посту или строке выгрузки, последняя строка — «Сохрани результат сам, как в правилах». Сохраните ТЗ в заметках.
  5. Отдайте ТЗ Claude Code в новой сессии. Дождитесь отчёта агента, откройте результат на github.com и сверьте его с файлом из критерия готовности. Codex или Copilot тоже можно: их pull request попросите слить Claude Code (урок 16).
  6. Проведите минимум две итерации с замечаниями по чеклисту урока 22 — в той же сессии: каждое — конкретный пример «файл → ожидал → получил» плюс фраза «ничего другого не меняй». Принимайте результат только после исправлений.
  7. Загрузите 1–2 новых файла через Upload files и попросите агента запустить инструмент снова. Проверьте, что по новым файлам результаты появились, а старые не изменились по содержанию.
  8. Приведите README в порядок — задачей агенту: разделы «что делает», «как пользоваться», «чего не учитывает».
  9. Напишите «защиту» из пяти предложений: что делает инструмент, кому полезен, что агент сделал плохо, как вы это исправили, что проверили вручную. Отправьте коллеге или клиенту вместе с доступом к репозиторию или с выгрузкой результата — скачанной таблицей или отчётом.

Критерии приёмки

Отмечайте только то, что проверили своими глазами. Чеклист и квиз ниже засчитывают контрольную автоматически.

  • Новый репозиторий существует, он Private, это не marketing из модуля 6; в нём нет персональных данных людей — имён, почт и телефонов клиентов и подписчиков.
  • В новом репозитории есть AGENTS.md и CLAUDE.md с разделом «Как сохранять работу»; создал и сохранил их агент.
  • ТЗ написано своими словами по шаблону урока 23 и сохранено; в нём есть критерий готовности с конкретным файлом и ожидаемым результатом по нему.
  • Агент сделал минимум две итерации по моим замечаниям; замечания с примерами «файл → ожидал → получил» видны в сессии.
  • По отчёту агента в каждой задаче тронуты только ожидаемые файлы, исходные посты и выгрузки не изменены, данные никуда не отправляются, ключей и паролей нет.
  • На GitHub я не нажимал(а) ничего, кроме Upload files и Commit changes: ветки, сохранение и слияние делал агент.
  • Результат по файлу из критерия готовности сходится с самим файлом — я открыл(а) их рядом и сверил(а), включая цифры.
  • После загрузки новых файлов агент запустил инструмент снова: по новым файлам результаты появились, старые не изменились по содержанию.
  • README отвечает на три вопроса: что делает инструмент, как пользоваться, чего не учитывает.
  • «Защита» из пяти предложений написана и отправлена коллеге или клиенту вместе с доступом к репозиторию или выгрузкой результата.

Проверка понимания

Чего не хватает в запросе «Проверь этот пост»?

  • Вежливого обращения к ИИ и благодарности в конце
  • Роли и контекста (какая площадка, какая аудитория и цель), задачи (что именно проверить), формата ответа и ограничений: цитировать, не додумывать
  • Названия модели, которая должна отвечать

Без контекста и формата ИИ сам решит, что считать проблемой, и ответит общими словами. Запрос из роли, задачи, контекста, формата и ограничений даёт проверяемый ответ.

В summary.md инструмент пишет для кампании «Вебинар-октябрь»: CTR 12 %. В выгрузке у неё 9000 показов и 54 клика. Что вы делаете перед тем, как отправить таблицу клиенту?

  • Доверяю: программа считает точнее, чем я на калькуляторе
  • Спрашиваю агента «ты уверен?» и отправляю, если он подтвердит
  • Пересчитываю по выгрузке: клики ÷ показы × 100 — при 54 кликах на 9000 показов CTR 0,6 %, а не 12; пишу агенту замечание «проверь формулу»

Программа может посчитать CTR не от показов, а, например, от расхода — и цифра будет выглядеть убедительно. «Ты уверен?» — не проверка. Первоисточник — выгрузка.

Агент пишет в отчёте: «Открыл pull request и сразу слил его в main». Что это значит для вас?

  • Нужно зайти на GitHub и подтвердить слияние кнопкой
  • Изменения ещё не сохранены и пропадут, если закрыть вкладку
  • Агент сам сохранил работу в основную версию репозитория; мне остаётся открыть результат и сверить его с файлами

Pull request и слияние — слова из отчёта: так агент описывает сохранение. Делать с ними ничего не нужно, а если результат плох — «верни как было», и агент найдёт прошлую версию сам.

Вы делаете свод кампаний и хотите загрузить в репозиторий вместе с выгрузкой кампаний базу адресов рассылки из CRM — с именами и почтами подписчиков. Почему базу нельзя, даже если репозиторий приватный?

  • Это персональные данные людей: они не должны уходить ни на GitHub, ни в машину агента, приватность репозитория этого не меняет. Выгрузку кампаний загружать можно
  • GitHub не принимает файлы .csv
  • Агент не умеет читать выгрузки, в которых есть суммы

Приватность защищает от посторонних на GitHub, но файлы всё равно покидают вашу организацию: лежат на серверах GitHub и обрабатываются в машине агента. Поэтому персональные данные — никогда, а посты и цифры кампаний — можно. Правило урока 09 действует и здесь.

Где выполняется программа, которую агент написал для вашего репозитория?

  • На вашем компьютере — поэтому сначала Python должен появиться у вас
  • В облачной виртуальной машине агента: он ставит там библиотеки, запускает программу на файлах репозитория и сам сохраняет результат
  • На серверах GitHub при каждом открытии репозитория

Вы ничего не устанавливаете. Агент клонирует репозиторий в свою машину, запускает программу там и сохраняет результат. Файлы уходят только в эту машину и в ваш репозиторий.

В отчёте агент пишет, что добавил отправку текстов постов на внешний сервис «для более точного анализа» и заодно переделал формат summary.md, хотя вы просили только добавить контент-план. Ваши действия?

  • Оставить: точный анализ полезен, а к новому формату можно привыкнуть
  • Оставить контент-план, а про сервис спросить потом
  • Не принимать: отправка текстов на чужой сервис — красный флаг; попросить отменить всё, что сделано в этой задаче, и поставить контент-план заново отдельной задачей с запретом на внешние сервисы и на изменение summary.md

Файлы не должны уходить никуда, кроме машины агента и репозитория, даже в окружении full. Изменения вне задачи ломают то, что работало. Одна задача — одна сессия: так понятно, что проверять и что откатывать.

Если не получается

Программа есть, результатов в репозитории нет

Обычно в ТЗ не было слова «запусти». Напишите в ту же сессию: «Запусти программу у себя на всех файлах из папки … и положи результаты в …; в отчёте напиши, как проверить. Сохрани результат сам, как в правилах». Сессия закрыта — новая сессия с той же фразой и уточнением «программа уже лежит в репозитории, не переписывай её».

Результат не сходится с постом или выгрузкой

Не чините сами и не пишите «работает неправильно». Опишите агенту пример: файл, пункт или число, что ожидали, что получили, — и добавьте «ничего другого не меняй». Перед этим убедитесь, что смотрите свежий результат: агент написал «Сохранил в main», и вы обновили страницу файла.

Агент не видит файлы

Проверьте три вещи: файлы загружены и видны на github.com; Claude GitHub App установлено на новый репозиторий, а не только на marketing; в селекторе репозитория выбран именно он. Агент видит только то, что лежит в репозитории, к которому у него есть доступ.

Если непонятно, где именно ошибка, — не угадывайте, спросите ИИ в обычном чате. Готовый запрос на примере контент-плана:

Запрос к ИИ
Я маркетолог, не программист. Мой инструмент — программа на Python в приватном репозитории на GitHub; её написал и запускает ИИ-агент, я только ставлю задачи и проверяю результат. Инструмент собирает контент-план: читает посты из папки posts/ и пишет таблицу contentplan.md с датой, площадкой и целью каждого поста.
Проблема: для поста posts/post-keis.md в столбце «дата» стоит «не указано», хотя в шапке поста написано «дата: 21.11.2026».
Задача:
1) объясни, в чём, скорее всего, причина — простыми словами, без программистских терминов;
2) напиши текст замечания для ИИ-агента, чтобы он исправил только это и ничего другого не трогал;
3) предложи ещё два контрольных примера записи даты в шапке, которые поймают ту же ошибку, если она вернётся.
Файл программы и пост я прикрепил к этому сообщению из репозитория.

Поздравляем — это финал. Два инструмента для маркетинга, сделанных по вашему заданию, и навык, который теперь не отнять: поставить задачу, проверить, принять. Остался один короткий урок — и сертификат: он появится на странице сертификата, когда все уроки отмечены пройденными.
