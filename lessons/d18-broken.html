Когда ИИ сделал не то

Пять типовых ситуаций — и все решаются кнопками на GitHub и одним сообщением агенту. Главная мысль урока: пока вы не нажали Merge, в репозитории ничего не изменилось; а что изменилось — откатывается кнопкой.

Почему можно не бояться

PR от агента — предложение в отдельной ветке. Договоры, чеклист и шаблоны в main его не видят. Плохой PR можно держать открытым неделю, закрыть, попросить переделать — ни один файл не изменится. Меняется всё только после Merge pull request → Confirm merge.

Слили и пожалели — у слитого PR есть кнопка Revert: GitHub готовит обратное изменение, вы его сливаете, файлы возвращаются к прежнему виду. Ни плохой PR, ни откат из истории не исчезают — история для того и нужна.

PR открыт — в main ничего не изменилось→ Merge — изменилось→ Revert — вернулось

Сценарий 1. Агент сделал не то, что просили

Просили таблицу договоров — получили пересказ каждого договора на абзац

Не сливайте. Дальше два пути — по объёму переделки.

  • Поправимо — не так несколько строк: замечание с конкретикой в той же сессии (Claude Code — в чат, Codex — в задачу, Copilot — комментарием в PR): файл, строка, что ожидали, что получили. Агент пришлёт новый коммит в тот же PR.
  • Переделывать всё — агент понял задачу иначе: Close pull request и новая задача новой сессией с уточнённым ТЗ. Обычно не хватало примера результата («таблица с такими столбцами») и границ («остальное не трогать»).

Замечание, которое не сработает

«Не то. Переделай нормально».

Замечание, которое сработает

«В README нужна таблица, а не абзацы: столбцы файл — стороны — предмет — дата — срок действия, по одной строке на договор. Пересказы убери. Данные только из текста договоров».

Сценарий 2. Слили, а в README ерунда

Нажали Merge, открыли README — таблица развалилась или половина данных выдумана

Откат — кнопка у слитого PR плюс один обратный PR. Степпер проведёт по экранам.

Слитый PR остался во вкладке Pull requests среди закрытых. Откройте его: внизу вкладки Conversation, рядом с отметкой о слиянии, — кнопка Revert.

Переписать README одним словом Merged

Revert1

GitHub сам подготовит обратное изменение — отмену каждой строки плохого PR — в отдельной ветке и откроет форму нового pull request. Править ничего не нужно: нажмите Create pull request.

Open a pull request

Revert "Переписать README одним словом"
Create pull request

Зелёным показано то, что вернётся, красным — то, что уберётся. Тронуты должны быть те же файлы, что и в плохом PR, и ничего больше.

Merge pull request → Confirm merge → Delete branch. README снова такой, каким был до плохого PR. В истории коммитов остались оба — плохой и запись, начинающаяся с Revert.

Revert откатывает PR целиком. Плоха одна строка, а остальное хорошо — не откатывайте, а поставьте агенту точечную задачу: «исправь строку про договор аренды, остальное не трогай».

Сценарий 3. Агент изменил договоры, хотя не просили

В Files changed рядом с README — файлы из contracts/

Красный флаг из урока 17: документы — первоисточник, агент не меняет их ни «для единообразия», ни «исправляя опечатки». Нажмите Close pull request, даже если README получился хорошим: разбирать, что именно изменилось в договоре, дороже, чем переделать README. PR уже слит — сценарий 2, Revert.

Правило на будущее: в каждом ТЗ, даже самом коротком, последняя строка — «файлы в contracts/ не менять». Что не написано — агент додумает сам.

Сценарий 4. Два агента правят одно и то же

Второй PR пишет: This branch has conflicts that must be resolved

Вы запустили две задачи параллельно — «добавь в README глоссарий» и «добавь в README раздел о сроках». Обе сессии изменили одни и те же строки, и после слияния первого PR второй слить нельзя: GitHub не знает, какой вариант правильный. Это конфликт слияния.

🐙 GitHubConversationFiles changed

This branch has conflicts that must be resolved

Resolve conflictsClose pull request

Кнопку Resolve conflicts с веб-редактором не нажимайте: разбирать конфликт руками — работа программиста, а не ваша. Закройте второй PR (Close pull request) и поставьте его задачу заново, когда первый слит: агент возьмёт актуальный README, и конфликта не будет.

Одна задача за раз. Пока PR не слит или не закрыт, следующую задачу в этот репозиторий не ставьте. Параллельно можно работать только над разными файлами — и даже тогда сливайте по одному.

Сценарий 5. Не понимаю, что вижу

Незнакомая надпись, серая кнопка, новое окно

Не угадывайте. Скопируйте текст с экрана дословно или сделайте скриншот — Claude и ChatGPT читают картинки — и спросите ИИ по форме: что делал, что ожидал, что увидел, текст ошибки. Запрос заполнен примером, подставьте свою ситуацию.

Запрос к ИИ
Я юрист, не программист. Работаю с ИИ-агентом (Claude Code в браузере) в приватном репозитории contracts на GitHub. Git руками не делаю: только проверяю pull request, оставляю замечания и нажимаю Merge.
Что делал(а): слил(а) первый PR агента (раздел о сроках в README), затем открыл(а) второй PR от другой сессии (глоссарий в README) и хотел(а) слить его.
Что ожидал(а): кнопка Merge pull request, затем Confirm merge.
Что увидел(а): кнопка слияния недоступна, над ней надпись про конфликты и кнопка Resolve conflicts.
Текст с экрана (дословно): This branch has conflicts that must be resolved.
Объясни простыми словами, что произошло и потеряно ли что-нибудь. Затем предложи самый простой путь без ручного разбора конфликта: какие кнопки нажать на GitHub и что написать агенту. Если есть риск что-то потерять — предупреди заранее.

Что бы вы сделали?

Юрист слил PR, в котором агент добавил в README таблицу из пяти договоров. Через неделю коллега заметил, что срок действия договора поставки указан неверно; остальные четыре строки верны, и коллеги уже ссылаются на таблицу. Revert или новая задача агенту?

Новая задача. Revert откатит весь PR — исчезнут и четыре верные строки, которыми уже пользуются. Поставьте точечную задачу: «В README исправь строку про contracts/dogovor-postavki.md: срок действия — дословно из п. 10.1 договора. Остальное не трогай», проверьте PR по чеклисту и слейте. Revert — когда плохо всё или вред от ошибки больше пользы от остального: например, даты выдуманы по всем договорам, а коллеги уже опираются на таблицу.

Проверьте себя

PR от агента открыт три дня, вы его не сливали. Что изменилось в файлах репозитория?

  • Ничего: изменения лежат в ветке агента, пока вы не нажмёте Merge
  • README уже обновился, остальные файлы нет
  • Через три дня GitHub сливает PR сам

Открытый PR — только предложение. Файлы в main не меняются без вашего Merge pull request → Confirm merge.

Слили PR, а README испорчен. Самый короткий путь назад?

  • Удалить репозиторий и загрузить документы заново
  • Попросить агента написать README с нуля
  • Нажать Revert у слитого PR, создать обратный PR и слить его

Revert возвращает прежнюю версию за минуту, ничего не выдумывая. Написать заново — новая работа агента с новыми рисками.

Второй PR показывает «This branch has conflicts that must be resolved». Что делать?

  • Нажать Resolve conflicts и выбрать правильный вариант строк вручную
  • Закрыть второй PR и поставить его задачу заново после слияния первого
  • Слить первый PR ещё раз

Разбор конфликта руками — работа программиста. Агент, запущенный после слияния первого PR, сделает то же без конфликта.

Вместе с README агент «поправил опечатки» в двух договорах в contracts/. PR ещё не слит.

  • Слить: опечатки в договорах — это полезно
  • Слить README, а договоры потом вернуть через History
  • Закрыть PR и добавить в ТЗ строку «файлы в contracts/ не менять»

Документы меняет только человек. Разбирать, что именно агент «поправил», дороже, чем закрыть PR и поставить задачу с границами.

Практика

Сломайте и почините — специально, пока это ничего не стоит. Поставьте агенту намеренно плохую задачу: «Перепиши README одним словом» (переспросит — подтвердите). Получите PR, посмотрите Files changed и закройте его без слияния. Затем слейте любой PR — из урока 15, если он ещё открыт, или новый с задачей «добавь в конец README строку: Учебный репозиторий курса по ИИ» — и откатите его через Revert.

  • PR «README одним словом» получен; в Files changed видно, что README сократился до строки; PR закрыт кнопкой Close pull request, README в репозитории не изменился.
  • Другой PR слит: Merge pull request → Confirm merge; изменение видно в README.
  • У слитого PR нажата кнопка Revert, обратный PR создан и слит.
  • README вернулся к прежнему виду; в истории коммитов есть и слияние, и запись, начинающаяся с Revert.
  • В следующих ТЗ будет строка «файлы в contracts/ не менять», а задачи пойдут по одной.

Теперь ошибки агента не страшны. Вы умеете не пускать плохое в репозиторий и возвращать как было одной кнопкой. Впереди контрольная модуля: две задачи агенту, два ревью и один откат.
