Доработки и повторные запуски

Инструмент работает — теперь его нужно развивать, не ломая. Вторая итерация, претензия из шаблона, идёт по трём правилам; в конце — пять готовых задач агенту.

Три правила доработки

Одна доработка — одна задача — один PR

Претензия — одна задача, реестр документов — другая. В одном PR вы не сможете принять первое и отклонить второе, а при откате потеряете оба.

«Не трогай то, что работает» — в каждом запросе

Агент охотно «улучшает» всё, до чего дотянется. Называйте, что менять нельзя: check_contracts.py, reports/, contracts/, — и сверяйте список файлов в Changes.

Новая сессия для новой задачи

Каждая сессия — своя ветка. Ветка первой задачи слита и удалена; новая задача начинается с чистой сессии на main, где инструмент уже лежит. В старой сессии агент тащит контекст прежней задачи.

Вторая итерация: претензия из шаблона

В templates/pretenziya.md — шаблон претензии с полями {контрагент}, {договор}, {сумма}, {срок}. Агент подставит в них данные из договора и сохранит документ в documents/. Семь шагов.

На claude.ai/code начните новую сессию, не продолжайте вчерашнюю: репозиторий contracts, ветка main (в ней уже лежит инструмент), режим Accept edits.

Текст готовый. Три защитные фразы: «программу проверки не трогай», «отчёты не пересоздавай», «покажи, откуда взято каждое значение». Первые две берегут то, что работает, третья делает результат проверяемым.

Запрос к агенту — вторая итерация

Сделай это для contracts/dogovor-postavki.md. Программу проверки не трогай; отчёты не пересоздавай. В описании PR покажи, какие поля шаблона заполнены и откуда взято каждое значение.

Агент читает шаблон и договор, пишет отдельную программу генерации (имя файла выберет сам), запускает её у себя и кладёт претензию в documents/.

Генерация — в отдельном файле make_pretenziya.py; check_contracts.py и reports/ не трогал. Ветка запушена.

Откройте карточку Changes. Ожидаемо: новый документ в documents/, новый файл программы генерации, изменённый README.md. Есть check_contracts.py или файлы из reports/ — агент нарушил запрет. Не разбирайтесь, что он поменял: попросите вернуть.

На GitHub: Merge pull request → Confirm merge → Delete branch. Откройте documents/ — претензия читается в браузере. Это черновик: перед отправкой юрист дорабатывает его, как документ стажёра.

Повторный запуск на новых документах

Инструмент не следит за репозиторием: новые файлы он увидит, когда вы поставите задачу. Загрузите договоры в contracts/: Add file → Upload files → Commit changes — можно сразу несколько. Затем новая сессия на main:

Запрос к агенту — только новые файлы
Запусти проверку только для новых файлов в contracts/ — тех, у которых нет отчёта в reports/. Старые отчёты не пересоздавай, программу не меняй. Добавь в summary.md строки по новым договорам, остальные строки не трогай. В описании PR перечисли проверенные файлы.

Затем Create PR, сверить три строки нового отчёта, Merge pull request. Если summary.md разошёлся с отчётами — например, после удаления договора, — не правьте таблицу руками, попросите агента пересобрать её по reports/:

Запрос к агенту — обновить сводку
Пересобери summary.md по всем отчётам из reports/: по строке на отчёт, те же колонки. Отчёты, программу и документы не меняй. В описании PR перечисли добавленные, удалённые и изменённые строки.

Как агент ломает инструмент и как не допустить

Вы просите слишком много за раз

Пять пожеланий в одном сообщении — половина сделана, половина «почти», всё в одном PR: принять частями нельзя, откатить — только целиком. Одна задача на сессию.

Агент меняет программу при доработке

Добавляя претензию, он «заодно» переписывает проверку — отчёты незаметно меняются. Фраза «не трогай» в запросе плюс список файлов в Changes. Тронул — «верни к состоянию main».

Длинные сессии

После десятка замечаний в одной сессии агент забывает ранние ограничения и смешивает задачи. После Merge сессию закрывайте; новая правка — новая сессия с именем файла и ссылкой на README.

Проверьте себя

Почему вторую итерацию делают в новой сессии, а не в той, где создавали инструмент?

  • Старая сессия удаляется автоматически после Create PR
  • Каждая задача — своя ветка; прежняя слита и удалена, а новая сессия начинается с main, где инструмент уже лежит
  • Чтобы не расходовать лимиты тарифа

Сессия живёт после PR, но её ветка уже влита в main. Новая задача на чистом main — проще для агента и прозрачнее для вас.

В Changes PR с генерацией претензии оказались check_contracts.py и все файлы из reports/. Что делать?

  • Слить: отчёты пересозданы из тех же договоров, значит, одинаковые
  • Не сливать; попросить вернуть эти файлы к состоянию main и объяснить, что менялось
  • Исправить отчёты карандашом на GitHub

Вы просили не трогать программу и отчёты. Пересозданные отчёты могут отличаться незаметно — проверять их целиком дороже, чем вернуть.

В contracts/ загрузили два новых договора. Как получить отчёты?

  • Подождать: агент заметит новые файлы и запустит проверку
  • Попросить пересоздать все отчёты заново
  • В новой сессии попросить проверить только файлы без отчёта, старые отчёты не пересоздавать

Агент работает только по вашей задаче. Пересоздавать всё — дольше, дороже и заставляет перепроверять уже принятые отчёты.

Практика

Пройдите степпер и сделайте один повторный запуск. Отмечайте только проверенное.

  • Вторая итерация слита отдельным PR; в Changes этого PR не было check_contracts.py и файлов из reports/.
  • Каждое поле претензии я сверил(а) с указанным пунктом договора; выдуманные значения заменены или отсутствуют.
  • Новый договор загружен через Upload files и проверен задачей «только новые файлы»; PR слит.
  • В summary.md столько строк, сколько договоров в contracts/.

Инструмент растёт, а не ломается. Следующий урок — как проверять результат инструмента, не читая код.
