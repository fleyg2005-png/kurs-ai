Контрольная 6: инструмент по вашему ТЗ

Без подсказок и степперов: сами, от ТЗ на свой инструмент до слитого PR и повторного запуска на новой карточке. Всё это вы делали в уроках 19–22.

Задание

  1. Выберите инструмент — не проверку карточек по чеклисту из урока 20, а свой: свод цен и остатков; отчёт «какие товары чаще всего ругают и за что»; таблица «товар — вопросы покупателей без ответа»; переименование карточек по единому шаблону. Условие: результат можно проверить по карточкам и выгрузке отзывов.
  2. Напишите ТЗ по шаблону урока 19: что есть, что сделать, ограничения, критерии готовности. В ограничениях — «данные только из файлов репозитория», «файлы никуда не отправлять», «карточки в tovary/ и выгрузку в otzyvy/ не менять» (для переименования — «только переименовывать, содержимое не трогать»). И обязательно: «запусти у себя и положи результат в репозиторий».
  3. Отдайте ТЗ агенту в новой сессии — Claude Code, Codex или Copilot cloud agent — и дождитесь pull request.
  4. Проведите ревью по чеклисту урока 22: минимум два замечания с конкретикой — файл, строка, что на самом деле в карточке или в выгрузке. Дождитесь исправлений.
  5. Слейте PR на GitHub.
  6. Загрузите новую карточку (или свежую выгрузку отзывов) через Upload files и запустите инструмент повторно — отдельным PR; проверьте и слейте.
  7. Убедитесь, что в README.md есть раздел «Как пользоваться». Нет — ещё одна задача агенту.

Критерии приёмки

Отмечайте только то, что проверили сами. Чеклист и квиз засчитывают контрольную автоматически.

  • Моё ТЗ содержит четыре части — что есть, что сделать, ограничения, критерии готовности — и хотя бы один критерий называет конкретный файл.
  • Агент сам написал программу, запустил её у себя и положил результат в репозиторий: в PR и программа, и файлы результата.
  • В Files changed нет изменений в tovary/, checklist.md и otzyvy/ (для переименования — только переименование, без правок внутри файлов).
  • Три значения результата я сверил(а) с карточками и выгрузкой: названия, цены и цитаты найдены дословно, одна вычисленная цифра пересчитана руками.
  • В PR минимум два моих замечания; после них агент прислал исправления, где они учтены.
  • PR слит на GitHub (Merge pull request → Confirm merge); результат читается в репозитории как текст.
  • Повторный запуск на новой карточке или свежей выгрузке сделан отдельным PR, который тоже слит; старые результаты не пересозданы.
  • В README.md есть раздел «Как пользоваться», понятный коллеге: как добавить карточку и запустить инструмент.

Проверка понимания

Из каких частей состоит ТЗ на инструмент для маркетплейса?

  • Цель, аудитория, дизайн, сроки
  • Что есть, что сделать, ограничения, критерии готовности
  • Список библиотек, код, тесты, лицензия

Агенту нужно знать, с чем он работает, что должно получиться, чего нельзя и как понять, что готово.

Где агент запускает программу, которую написал?

  • На вашем компьютере
  • В кабинете маркетплейса, рядом с карточками
  • В своей виртуальной машине в облаке; результат присылает в репозиторий

Вы ничего не устанавливаете, а к кабинету площадки агент не подключён — он видит только репозиторий.

Что считается результатом работы инструмента?

  • Файлы в репозитории — сводки, отчёты, черновики ответов, — присланные через PR
  • Текст ответа агента в чате сессии
  • Ссылка на сессию в коммите

Ответ в чате пропадёт, файлы в репозитории останутся — их можно показать и проверить.

Что такое выборочная проверка результата?

  • Прочитать программу и найти в ней ошибки
  • Сверить несколько значений с карточками дословно и пересчитать одну вычисленную цифру по выгрузке
  • Спросить агента, всё ли верно

Код вы не читаете, а «всё верно» от агента — не проверка. Убеждает только сверка с файлами.

Какая ситуация — красный флаг: PR сливать нельзя?

  • Агент вынес подготовку ответов на отзывы в отдельный файл программы
  • Агент предлагает прогнать выгрузку отзывов через внешний онлайн-сервис
  • Агент пометил один пункт «неясно» и объяснил почему

Файлы должны оставаться в репозитории и в машине агента. Отдельный файл программы и честное «неясно» — нормальная работа.

Зачем правило «одна доработка — один PR»?

  • GitHub не позволяет менять больше одного файла за PR
  • Агент не умеет делать две вещи в одной сессии
  • Чтобы каждое изменение можно было проверить, принять или откатить отдельно

PR — единица приёмки и отката: смешав две доработки, вы не сможете принять одну и отклонить другую.

Если не получается

Агент не смог разобрать выгрузку

Попросите его определить разделитель и кодировку самому и перечислить строки, которые не читаются; не помогло — выгрузите отзывы заново и загрузите файл через Upload files. Нечитаемые строки агент должен назвать, а не пропустить молча.

Результат не сходится с файлами

Не сливайте; замечание с конкретикой: файл, строка, что в карточке. Расходится почти всё — Close pull request, усильте в ТЗ ограничения («данные только из файлов, значения дословно») и запустите новую сессию.

Агент переделал всё подряд

В Changes десятки файлов, включая запрещённые. Не разбирайте по частям: попросите вернуть лишнее к состоянию main; PR безнадёжен — закройте и разделите задачу на две.

Причина непонятна — спросите ИИ в обычном чате:

Запрос к ИИ
Я поставил задачу ИИ-агенту в приватном репозитории shop на GitHub (карточки товаров, выгрузка отзывов, шаблоны).
Агент: [Claude Code / Codex / Copilot cloud agent].
Моё ТЗ: [текст целиком].
Что сделал агент: [какие файлы появились или изменились, что написано в описании PR].
Что не так: [что вижу и что ожидал; если агент сообщил об ошибке — её точный текст].
Назови 3 самые вероятные причины, для каждой — как проверить за минуту по файлам в репозитории, и предложи текст замечания агенту, которое исправит проблему и не тронет лишнего.
