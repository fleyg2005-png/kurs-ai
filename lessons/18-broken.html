Когда что-то сломалось

Главная мысль урока помещается в одну фразу: всё, что хоть раз попало в git, восстановимо. Поэтому паниковать не надо — надо знать пять сценариев. Они покрывают почти всё, что случается с не-программистом.

Почему можно не бояться

В обычной папке «удалил» значит «пропало». В репозитории каждый коммит хранится навсегда: удалённый файл, затёртый абзац, неудачная правка — всё лежит в истории и возвращается за минуту. Git не стирает старое, а добавляет новое поверх. Даже откат — это не удаление, а ещё один коммит, который возвращает прежнее состояние.

Отсюда правило: сломалось — не пересоздавайте репозиторий и не удаляйте файлы «чтобы начать с чистого листа». Определите, какой из пяти сценариев перед вами, и идите по шагам.

Сценарий 1. Плохой коммит

Сделали коммит — и стало хуже: сайт сломался, текст пропал

  1. На главной странице репозитория нажмите ссылку с числом коммитов (иконка часов) — откроется история.

  2. Найдите плохой коммит (обычно верхний) и откройте его, нажав на подпись. По красным и зелёным строкам убедитесь, что это он.

  3. На странице коммита найдите Revert (откатить) — кнопку справа вверху или пункт в меню … рядом с ней.

  4. GitHub подготовит обратное изменение — то, что отменяет каждую строку плохого коммита, — в отдельной ветке и предложит открыть pull request. Создайте его и слейте: Create pull request → Merge pull request → Confirm merge. В истории появится запись, начинающаяся с Revert, а файлы вернутся к прежнему состоянию. Плохой коммит из истории никуда не исчезает — и это нормально.

  5. Если изменение пришло через pull request, ещё проще: у слитого PR есть кнопка Revert, которая делает то же самое. А если кнопки нигде нет — сценарий 2 ниже работает всегда.

Сценарий 2. Испортили один файл

Переписали index.html, сделали ещё несколько коммитов, а нужен абзац недельной давности

  1. Откройте файл в репозитории и нажмите History (история) справа над содержимым — это история только этого файла.

  2. Найдите коммит с датой, когда файл был ещё хорош, и откройте его. GitHub покажет, что менялось в файле в тот момент: удалённые тогда строки — красным, добавленные — зелёным.

  3. Скопируйте нужный текст, вернитесь к текущей версии файла, нажмите карандаш и вставьте его на место.

  4. Сделайте коммит: Вернуть раздел «Опыт» из версии от 12 октября. Это новый коммит поверх истории — остальные правки остаются на месте.

Сценарий 3. Конфликт в pull request

Pull request пишет «This branch has conflicts that must be resolved»

Конфликт слияния возникает, когда одну и ту же строку поменяли в двух местах: в вашей ветке и в main. Git не знает, какой вариант правильный, и спрашивает вас. Это не поломка, а вопрос.

  1. В pull request нажмите Resolve conflicts (разрешить конфликты). Откроется веб-редактор с файлом, где спорные места обозначены маркерами.

  2. Найдите блок между <<<<<<< и >>>>>>>. Сверху, до =======, — вариант из вашей ветки; снизу — из main.

    <ul> <<<<<<< update-list <li>Веду учёт малого бизнеса 13 лет</li> ======= <li>Веду учёт малого и среднего бизнеса 12 лет</li> >>>>>>> main </ul>

  3. Оставьте правильный вариант строки (или напишите объединённый) и удалите три строки-маркера целиком. В файле не должно остаться ни одного символа из <<<<<<<, ======= и >>>>>>>.

  4. Нажмите Mark as resolved (отметить как решённый), затем Commit merge. Pull request снова можно слить: Merge pull request → Confirm merge.

Правило, после которого конфликтов почти не бывает. Один человек (или один агент) правит один файл в один момент времени. Две ветки, которые трогают разные файлы, сливаются без вопросов. Работаете с агентом — не правьте руками тот файл, над которым он сейчас работает.

Сценарий 4. Сайт не обновился или показывает 404

Коммит сделан, а по адресу сайта — старая версия или страница с ошибкой 404

  1. Подождите. Публикация занимает от 1 до 10 минут, и повторные коммиты её не ускоряют. Обновите страницу с очисткой кеша (Ctrl+Shift+R) или откройте её в режиме инкогнито.

  2. Через 10 минут всё ещё не то — откройте Settings → Pages. Должно стоять: Source — Deploy from a branch, ветка main, папка /(root). Если не так — выставьте и нажмите Save.

  3. Проверьте имя файла в корне репозитория: строго index.html. Ошибки регистра (Index.html) и лишние расширения (index.html.txt) — самая частая причина 404.

  4. Проверьте, что репозиторий публичный: на бесплатном тарифе Pages для приватных не работает.

Сценарий 5. «Я не понимаю, что происходит»

Красная надпись, незнакомое окно, кнопка, которой вчера не было

Не угадывайте. Скопируйте текст ошибки (или сделайте скриншот — Claude и ChatGPT читают картинки) и отправьте ИИ по форме ниже. Четыре поля — что делали, что ожидали, что увидели, текст ошибки — дают ИИ всё, чтобы ответить точно. Запрос заполнен примером; подставьте свою ситуацию, текст ошибки — дословно.

Запрос к ИИ
Я работаю с GitHub через браузер, без установленных программ, я не программист.
Что я делал(а): в репозитории hello-ai открыл(а) pull request из ветки update-list в main и нажал(а) Merge pull request.
Что ожидал(а): изменения попадут в main, сайт на GitHub Pages обновится.
Что увидел(а): кнопка слияния недоступна, над ней надпись про конфликты.
Текст ошибки (дословно): This branch has conflicts that must be resolved.
Объясни простыми словами, что произошло. Затем дай пошаговую инструкцию для веб-интерфейса GitHub: какие кнопки нажимать и что я увижу после каждого шага. Если есть риск что-то потерять — предупреди заранее.

Что бы вы сделали?

Юрист ведёт в репозитории шаблоны договоров. В пятницу он через карандаш «поправил опечатку» в dogovor-postavki.md, сделал коммит и ушёл. В понедельник выяснилось, что при правке он случайно стёр весь раздел «Ответственность сторон» — 40 строк. После этого в файл успели внести ещё два коммита с другими правками. Что выбрать: Revert или History?

History. Revert пятничного коммита попытался бы отменить и строки, которых коснулись понедельничные коммиты, — и мог бы упереться в конфликт. Проще сценарий 2: открыть History у файла, найти коммит перед пятничным, скопировать раздел «Ответственность сторон», вставить его через карандаш и сделать коммит «Вернуть раздел об ответственности, стёртый 17 октября». Понедельничные правки останутся на месте. Правило: Revert — когда плохой коммит последний и его нужно отменить целиком; History — когда нужно вернуть кусок, а поверх уже есть другие изменения.

Проверьте себя

Что делает Revert?

  • Удаляет коммит из истории навсегда
  • Создаёт новый коммит, который отменяет изменения выбранного; сам выбранный коммит остаётся в истории
  • Возвращает весь репозиторий к самому первому коммиту

Git ничего не стирает. Откат — это ещё одна запись в истории, поэтому и его при желании можно откатить.

Когда возникает конфликт слияния?

  • Когда одну и ту же строку изменили и в ветке, и в main
  • Когда в репозитории больше ста коммитов
  • Когда в pull request больше одного файла

Разные файлы или разные строки git сливает сам. Спрашивает он только тогда, когда два варианта одной строки спорят между собой.

Сайт на Pages показывает 404 через минуту после коммита. Что сделать первым?

  • Удалить index.html и создать его заново
  • Пересоздать репозиторий
  • Подождать до 10 минут и обновить страницу с очисткой кеша

Публикация небыстрая. Только если через 10 минут ничего не изменилось, идите проверять Settings → Pages и имя файла.

Что должно остаться в файле после разрешения конфликта?

  • Оба варианта строки вместе с маркерами — GitHub сам выберет нужный
  • Только нужный текст, без единого маркера <<<<<<<, ======= и >>>>>>>
  • Маркеры можно оставить, они не видны на сайте

Маркеры — вопрос git к вам. Пока они в файле, файл сломан: на сайте они покажутся как обычный текст.

Практика

Сломайте и почините — специально, пока это ничего не стоит. В репозитории hello-ai откройте README.md через карандаш, удалите половину текста и сделайте коммит с сообщением Испортить README (учебный коммит). Затем откатите его по сценарию 1.

  • Сделал(а) намеренно плохой коммит: в README пропала часть текста, коммит виден в истории.
  • Открыл(а) плохой коммит в истории и нашёл(а) Revert (кнопку или пункт меню «…»).
  • Обратный pull request создан и слит; в истории появилась запись, начинающаяся с Revert.
  • README снова показывает полный текст; оба коммита — плохой и обратный — остались в истории.
  • Знаю, какой сценарий выбрать при 404 на сайте, а какой — при конфликте в pull request.

Теперь ломать не страшно. Вы знаете, что в git ничего не пропадает, и умеете возвращать как было тремя способами. Впереди контрольная: полный цикл с веткой, pull request и откатом — в своём репозитории.
