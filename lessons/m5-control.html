Контрольная 5: ветка и pull request

Без подсказок и степперов: проведите изменение сайта полным циклом — ветка, правка в github.dev, pull request, слияние, откат. Всё это вы делали в уроках 15–18 (ветки и PR — на симуляторе в уроке 17); теперь — в настоящем репозитории.

Задание

Репозиторий — из контрольной 4 (my-ai-notes) или hello-ai: любой, где включён GitHub Pages.

  1. Создайте ветку update-list: кнопка с именем ветки над списком файлов → ввести имя → Create branch update-list from main.
  2. Находясь в ветке update-list, нажмите . — github.dev откроется в этой ветке (её имя показано в строке состояния внизу слева; там не должно быть main). Добавьте в index.html новый раздел: заголовок <h2> и абзац или список. Нажмите Commit & Push.
  3. На github.com нажмите Compare & pull request, напишите заголовок и описание (2–3 предложения: что добавлено и зачем) → Create pull request.
  4. Во вкладке Files changed проверьте diff: зелёные строки — ваши, красных нет. Оставьте один комментарий к любой строке.
  5. Merge pull request → Confirm merge → Delete branch. Через 1–10 минут убедитесь, что раздел появился на сайте.
  6. На странице слитого pull request нажмите Revert и слейте обратный pull request. Убедитесь, что раздел с сайта исчез.
  7. По желанию: создайте codespace на main, сделайте любую правку и закоммитьте её из терминала (git add ., git commit -m "…", git push). Остановите codespace.

Критерии приёмки

Отмечайте только то, что проверили своими глазами. Чеклист и квиз ниже засчитывают контрольную автоматически.

  • Коммит с новым разделом сделан в ветку update-list, а не в main: в pull request виден именно он.
  • У pull request осмысленный заголовок и описание из 2–3 предложений.
  • Во вкладке Files changed я проверил(а) diff и оставил(а) комментарий к строке — он виден в обсуждении PR.
  • PR слит через Merge pull request → Confirm merge, ветка удалена, раздел появился на сайте.
  • Обратный PR, созданный кнопкой Revert, слит; раздел с сайта исчез, а в истории main есть и исходный коммит, и обратный.
  • Сайт по-прежнему открывается в режиме инкогнито без 404.
  • Я могу объяснить коллеге одной фразой, зачем нужна ветка и чем pull request отличается от коммита.

Проверка понимания

Зачем делать изменение в ветке, а не сразу в main?

  • Коммиты в ветке делаются быстрее
  • main и сайт остаются рабочими, а изменение можно проверить и обсудить до слияния
  • Без ветки GitHub не разрешает делать коммиты

Ветка — черновик рядом с рабочей версией. Pages публикует main, поэтому содержимое ветки на сайт не попадает до слияния.

Что происходит после Merge pull request → Confirm merge?

  • Коммиты ветки попадают в main; сайт из main обновится через несколько минут
  • Ветка переименовывается в main, а старый main удаляется
  • Pull request отправляется на проверку сотрудникам GitHub

Слияние переносит изменения в main. Ветку после этого можно удалить — её коммиты уже в основной истории.

Вы слили pull request, и сайт сломался. Самый быстрый безопасный способ вернуть как было?

  • Удалить репозиторий и создать заново
  • Нажать Revert у слитого PR и слить обратный pull request
  • Удалить index.html и написать его с нуля

Revert создаёт обратное изменение, не стирая историю. Сайт вернётся к прежнему виду, а причину можно искать потом.

Чего нельзя сделать в github.dev?

  • Изменить несколько файлов одним коммитом
  • Сделать коммит в ветку, а не в main
  • Открыть терминал и выполнить команду

github.dev — редактор без виртуальной машины. Терминал и запуск кода — только в Codespaces.

Какой бесплатный лимит Codespaces у личного аккаунта?

  • 10 часов в месяц, дальше нужна карта
  • 120 core-часов в месяц (60 часов на двухъядерной машине) и 15 ГБ хранилища
  • Без ограничений, пока репозиторий публичный

Часы тратятся, пока codespace запущен, хранилище — пока он существует. Останавливайте после работы, ненужные удаляйте.

Вы изменили index.html в ветке update-list и сделали коммит. Изменился ли сайт?

  • Да, сразу после коммита
  • Да, через 1–10 минут
  • Нет: Pages публикует main, сайт изменится только после слияния pull request

В этом смысл ветки: можно экспериментировать, сайт не трогается.

Если не получается

Нет плашки Compare & pull request

Она висит недолго. Откройте вкладку Pull requests и создайте pull request вручную, указав, что сливаете update-list в main. Если ветки в списке нет — коммит ушёл в main (см. запрос ниже).

github.dev открылся в main

Вернитесь на github.com, выберите update-list кнопкой с именем ветки над файлами и снова нажмите точку. Или в github.dev нажмите имя ветки в строке состояния внизу слева и выберите нужную.

Merge pull request неактивна, написано про конфликты

Пока вы правили ветку, та же строка изменилась в main (например, вами же через карандаш). Нажмите Resolve conflicts, уберите маркеры, оставьте нужный вариант — сценарий 3 из урока 18.

Если причина непонятна — не угадывайте, спросите ИИ. Запрос заполнен типичной ситуацией; опишите свою так же, по четырём полям.

Запрос к ИИ
Я делаю задание по GitHub в браузере, без установленных программ, я не программист.
Репозиторий публичный, ветки main и update-list, сайт на GitHub Pages публикуется из main.
Что я делал(а): открыл(а) github.dev клавишей «.», изменил(а) index.html и нажал(а) Commit & Push.
Что ожидал(а): коммит попадёт в ветку update-list, и я открою pull request.
Что увидел(а): коммит оказался в main — в строке состояния github.dev была ветка main; сайт уже обновился.
Объясни, что произошло. Предложи самый простой способ исправить это через веб-интерфейс GitHub, чтобы изменение оказалось в ветке update-list и прошло через pull request, а main вернулся к прежнему состоянию. Пошагово: какую кнопку нажать и что я увижу после каждого шага.

Сдали? Значит, вы умеете то, что программисты делают каждый день: менять в ветке, проверять в pull request, сливать и откатывать. Именно так вы будете принимать работу ИИ-агентов в модуле 6 — только код за вас напишут они.
