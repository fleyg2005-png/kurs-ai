Контрольная 5: ветка и pull request

Без подсказок и степперов: проведите изменение сайта полным циклом — ветка, правка в github.dev, pull request с проверкой, слияние, откат. Всё это вы делали в уроках 15, 16 и 18 и на симуляторе в уроке 17; теперь — в настоящем репозитории.

Задание

Работайте в репозитории из контрольной 4 (my-ai-notes) или в hello-ai — в любом, где включён GitHub Pages и сайт открывается.

  1. Создайте ветку update-list от main: кнопка с именем ветки над списком файлов → ввести имя → Create branch update-list from main.
  2. Откройте репозиторий в github.dev в этой ветке: находясь в ветке update-list, нажмите .. Имя ветки показано в строке состояния внизу слева — убедитесь, что там не main. Добавьте в index.html новый раздел: заголовок <h2> и абзац или список под ним. Сделайте коммит кнопкой Commit & Push.
  3. На github.com откройте pull request из update-list в main (плашка Compare & pull request → Create pull request). Заголовок — что сделано; описание — 2–3 предложения: что добавлено и зачем.
  4. Во вкладке Files changed проверьте diff: зелёные строки — именно те, что вы добавили, красных нет. Оставьте один комментарий к любой строке.
  5. Слейте: Merge pull request → Confirm merge → Delete branch. Через 1–10 минут убедитесь, что новый раздел появился на сайте.
  6. На странице слитого pull request нажмите Revert. GitHub создаст обратный pull request — слейте его так же. Убедитесь, что раздел с сайта исчез.
  7. По желанию: создайте codespace на main, сделайте любую правку и закоммитьте её из терминала (git add ., git commit -m "…", git push). Остановите codespace.

Критерии приёмки

Отмечайте только то, что проверили своими глазами. Чеклист и квиз ниже засчитывают контрольную автоматически.

  • Ветка update-list создана от main, и коммит с новым разделом сделан в неё, а не в main: в pull request виден ровно этот коммит.
  • У pull request осмысленный заголовок и описание из 2–3 предложений — что добавлено и зачем.
  • Во вкладке Files changed я проверил(а) diff и оставил(а) хотя бы один комментарий к строке — он виден в обсуждении PR.
  • PR слит через Merge pull request → Confirm merge, ветка удалена, новый раздел появился на сайте.
  • Обратный PR, созданный кнопкой Revert, слит; раздел с сайта исчез, а в истории main есть и исходный коммит, и обратный.
  • Сайт по-прежнему открывается в режиме инкогнито без 404.
  • Я могу объяснить коллеге одной фразой, зачем нужна ветка и чем pull request отличается от коммита.

Проверка понимания

Зачем делать изменение в ветке, а не сразу в main?

  • Коммиты в ветке делаются быстрее
  • main и сайт остаются рабочими, пока вы правите, а изменение можно проверить и обсудить до слияния
  • Без ветки GitHub не разрешает делать коммиты

Ветка — черновик рядом с рабочей версией. Pages публикует main, поэтому всё, что в ветке, на сайт не попадает, пока вы не сольёте pull request.

Что происходит после Merge pull request → Confirm merge?

  • Коммиты ветки попадают в main; если сайт публикуется из main, он обновится через несколько минут
  • Ветка переименовывается в main, а старый main удаляется
  • Pull request отправляется на проверку сотрудникам GitHub

Слияние переносит изменения в main. Ветку после этого можно удалить — её коммиты уже в основной истории.

Вы слили pull request, и сайт сломался. Самый быстрый безопасный способ вернуть всё как было?

  • Удалить репозиторий и создать заново
  • Нажать Revert у слитого PR и слить обратный pull request
  • Удалить index.html и написать его с нуля

Revert создаёт обратное изменение, не стирая историю. Через несколько минут сайт вернётся к прежнему виду, а причину можно спокойно искать потом.

Чего нельзя сделать в github.dev?

  • Изменить несколько файлов и закоммитить их одним коммитом
  • Сделать коммит в ветку, а не в main
  • Открыть терминал и выполнить команду

github.dev — редактор без виртуальной машины. Терминал и запуск кода — только в Codespaces.

Какой бесплатный лимит Codespaces у личного аккаунта?

  • 10 часов в месяц, дальше нужна карта
  • 120 core-часов в месяц (60 часов на двухъядерной машине) и 15 ГБ хранилища
  • Без ограничений, пока репозиторий публичный

Часы тратятся, пока codespace запущен, хранилище — пока он существует. Останавливайте после работы и удаляйте ненужные.

Вы изменили index.html в ветке update-list и сделали коммит. Изменился ли сайт на GitHub Pages?

  • Да, сразу после коммита
  • Да, через 1–10 минут
  • Нет: Pages публикует ветку main, сайт изменится только после слияния pull request

Это и есть смысл ветки: можно спокойно экспериментировать, сайт при этом не трогается.

Если не получается

Нет плашки Compare & pull request

Она показывается недолго после коммита в ветку. Откройте вкладку Pull requests и создайте pull request вручную, указав, что сливаете update-list в main. Если ветки в списке нет — коммит ушёл в main (см. запрос ниже).

github.dev открылся в main, а не в ветке

Вернитесь на github.com, выберите update-list кнопкой с именем ветки над файлами и снова нажмите точку. Или в самом github.dev нажмите на имя ветки в строке состояния внизу слева и выберите нужную.

Кнопка Merge pull request неактивна, написано про конфликты

Пока вы правили ветку, кто-то (возможно, вы же через карандаш) поменял ту же строку в main. Нажмите Resolve conflicts, уберите маркеры, оставьте нужный вариант — сценарий 3 из урока 18.

Если причина непонятна — не угадывайте, спросите ИИ. Запрос ниже заполнен типичной ситуацией; опишите свою так же — по четырём полям.

Объясни, что произошло. Предложи самый простой способ исправить это через веб-интерфейс GitHub, чтобы в итоге изменение было в ветке update-list и прошло через pull request, а main вернулся к прежнему состоянию. Пошагово: какую кнопку нажать и что я увижу после каждого шага.

Сдали? Значит, вы умеете делать то, что делают программисты каждый день: менять в ветке, проверять в pull request, сливать и откатывать. Именно так вы будете принимать работу ИИ-агентов в модуле 6 — только код за вас напишут они.
