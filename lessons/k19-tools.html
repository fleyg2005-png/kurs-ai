Какие инструменты для маркетинга может сделать ИИ

До сих пор агент делал разовую работу: прочитал посты — переписал README. Инструмент — следующий шаг: программа, которая лежит в репозитории и запускается снова на новых постах и свежих выгрузках. Что реально сделать с текстами и статистикой кампаний, где граница и как написать ТЗ.

Чем инструмент отличается от ответа в чате

Спросить в чате «есть ли в этом посте призыв к действию и ссылка с UTM-меткой» — быстро и годится для одного текста. Но на следующей неделе постов снова десять, и всё повторяется; ответ живёт в переписке, коллеги его не видят, а проверить, не пропущен ли пункт чеклиста, нечем.

Инструмент устроен иначе: правила записаны один раз в программе, программа лежит рядом с постами и выгрузками и запускается снова на новых файлах, а результат — отчёты и таблицы, которые открываются прямо на GitHub и проверяются по одному чеклисту.

Что агент может построить

В облачной машине агента есть Python; посты (.md) и выгрузки (.csv) он разбирает без подготовки. Всё, что сводится к «прочитать файлы из папки по правилам и записать результат в файлы», — его работа:

  • Проверка поста по чеклисту перед публикацией: отчёт по каждому посту — пункт, выполнено или нет, цитата.
  • Свод кампаний из выгрузки кабинета: по каждой кампании — показы, клики, CTR, расход, цена клика.
  • Проверка ссылок на UTM-метки по всем постам: таблица, где метка есть, а где потерялась.
  • Отчёт за месяц из шаблона по данным выгрузки — цифры и вывод по ним.
  • Таблица контент-плана из папки постов: файл — дата — площадка — цель — статус.
  • Поиск запрещённых обещаний («гарантируем результат», «лучший на рынке») по всем текстам сразу.
  • Раскладка и переименование постов по датам и площадкам по единому образцу.

Два слова о метриках из выгрузки, раз они будут считаться. CTR — это клики ÷ показы × 100, в процентах: 54 клика на 9 000 показов — CTR 0,6 %. Цена клика — расход ÷ клики: 12 420 ₽ на те же 54 клика — 230 ₽ за клик. Обе цифры агент посчитает из выгрузки, и обе вы сможете пересчитать на калькуляторе.

SMM

Проверка каждого поста по чеклисту перед публикацией, с цитатами. Таблица контент-плана из папки постов: даты, площадки, статусы согласования.

Email-маркетолог

Проверка писем рассылки: тема, длина, призыв, все ли ссылки с UTM-метками. Поиск запрещённых обещаний по всем выпускам сразу.

Перформанс-маркетолог

Свод кампаний из выгрузки кабинета с CTR и ценой клика. Отчёт за месяц из шаблона по той же выгрузке.

Контент-менеджер

Реестр всех текстов в папке: файл — дата — площадка — статус. Раскладка и переименование файлов по единому образцу.

Персональные данные — по-прежнему нет. Инструмент видит только то, что лежит в репозитории. Посты и статистика кампаний могут быть реальными, а имён, почт и телефонов клиентов и подписчиков там быть не должно (урок 09). Базы адресов для рассылок в репозиторий не попадают вовсе.

Где это работает — и где граница

Схема та же, что в модуле 5, только вместо README агент приносит программу и результат:

ТЗ→ Агент пишет программу→ Запускает на файлах→ PR: программа + отчёты→ Ваше ревью, Merge→ Новые посты — «запусти снова»

Программа выполняется в машине агента, не на вашем компьютере, и только по вашей просьбе: «добавил три поста, запусти проверку снова» — и приходит новый PR с новыми отчётами. Файлы никуда не уходят, кроме машины агента и репозитория.

Граница проходит по стенкам репозитория. Агент не публикует посты в соцсетях и рассылках, не запускает кампании и не забирает статистику из рекламных кабинетов: доступа туда у него нет, и курс этому не учит. Репозиторий — подготовительная кухня: тексты и отчёты готовятся здесь, а публикуете посты и выгружаете статистику (CSV из кабинета — в папку campaigns/) вы сами. И по расписанию программа сама не запустится: «каждый понедельник собирать свод» — дополнительная настройка (на GitHub — GitHub Actions), следующий уровень за рамками курса. Нужен результат — попросите агента.

Контент-менеджеру к завтрашнему созвону нужно свести три поста конкурса в одну таблицу. SMM-специалист каждую неделю готовит 8–10 постов, каждый перед публикацией проверяется по чеклисту, а отчёты читают редактор и клиент. Где инструмент, а где хватит чата?

Контент-менеджеру — чат: три файла, один раз, результат нужен сейчас и только ему. SMM-специалисту — инструмент: повторяется каждую неделю, постов много, результат читают коллеги. Три признака инструмента: повторяется, файлов больше десятка, результат нужен не только вам.

Структура ТЗ для инструмента

Четыре части: первые две определяют, что агент построит; третья защищает файлы; четвёртая даёт способ проверить результат за пять минут.

  1. Что есть — папки и файлы: где посты, где выгрузка кампаний, где правила (чеклист, шаблон отчёта).
  2. Что сделать — написать программу и назвать файл; запустить на всех файлах; положить результат в названные файлы; добавить в README раздел «Как пользоваться».
  3. Ограничения — данные только из файлов; посты, чеклист и выгрузку не менять; никуда не отправлять.
  4. Критерии готовности — проверяемый пример по конкретному файлу, ответ на который вы знаете заранее: «в отчёте по posts/post-rassylka.md пункт „Ссылка с UTM-меткой“ помечен „не выполнено“».
Шаблон ТЗ для инструмента
Сделай инструмент «НАЗВАНИЕ».

Что есть: папки и файлы — где посты, где выгрузка кампаний (.csv), где правила (чеклист, шаблон) и что в них.

Что сделать:
1. Напиши программу на Python (назовите файл, например check_posts.py), которая для каждого файла из папки … — опишите результат одного прогона: какой файл появляется, что в нём и в каком виде (таблица с такими столбцами).
2. Собери сводный файл по всем постам или кампаниям: имя файла и столбцы таблицы.
3. Запусти программу у себя на всех файлах и положи готовые результаты в репозиторий вместе с программой.
4. В README добавь раздел «Как пользоваться»: как добавить новый пост и как попросить тебя запустить инструмент снова.

Ограничения: данные брать только из файлов репозитория, ничего не додумывать — если в посте чего-то нет, писать «не выполнено». Файлы никуда не отправлять, кроме твоей рабочей машины. Посты, чеклист и выгрузку не менять.

Критерии готовности: для каждого поста есть результат; в сводной таблице столько строк, сколько файлов; один проверяемый пример по конкретному посту — в таком-то файле должно быть написано то-то (вы знаете это заранее). В описании PR перечисли, что сделано, что не получилось и как мне проверить результат за 5 минут.

Заполненный пример — ТЗ проекта «Проверка постов по чеклисту» — в следующем уроке; по нему вы получите первый инструмент.

Так не надо

«Сделай программу, которая анализирует наши посты и повышает CTR. Используй нейросеть, чтобы было умно».

Нет файлов и вида результата, а «повысить CTR» — не результат прогона, а пожелание: агент изобретёт что-то своё, и проверить его будет нечем.

Так надо

«Что есть: posts/ (четыре поста .md), checklist.md (10 пунктов), campaigns/campaigns.csv. Что сделать: программа check_posts.py; для каждого поста — отчёт в reports/ с таблицей пункт — выполнено/не выполнено/неясно — цитата; сводная summary.md по постам и кампаниям; запусти на всех. Ограничения: данные только из файлов; posts/, checklist.md и campaigns/ не менять; никуда не отправлять. Критерий: в отчёте по post-rassylka.md пункт „Ссылка с UTM-меткой“ — „не выполнено“».

Проверьте себя

Чем инструмент отличается от ответа ИИ в чате?

  • Инструмент использует более мощную модель
  • Программа лежит в репозитории, запускается снова на новых постах, а результат — файлы, которые видят коллеги
  • Инструмент работает без файлов в репозитории

Модель может быть той же. Разница — в повторяемости и в результате-файле вместо текста в переписке.

Где выполняется программа, которую написал агент?

  • На вашем компьютере, после установки Python
  • На серверах GitHub при каждом открытии репозитория
  • В облачной машине агента, по вашей просьбе; результат приходит как pull request

Вы ничего не устанавливаете. Агент запускает программу у себя; файлы не покидают его машину и репозиторий.

Инструмент проверил посты и собрал свод кампаний. Кто публикует пост и выгружает статистику из кабинета?

  • Вы сами: агент работает только с файлами репозитория, в соцсети и рекламные кабинеты он не ходит
  • Агент — после Merge у него появляется доступ к площадкам
  • GitHub публикует пост автоматически, в этом смысл Merge

Репозиторий — подготовительная кухня. Merge лишь принимает файлы в main; публикация и выгрузка статистики остаются вашими.

Что обязательно должно быть в критериях готовности ТЗ?

  • Название библиотеки для чтения .csv
  • Срок выполнения в минутах
  • Проверяемый пример по конкретному файлу, ответ на который вы знаете заранее

По примеру агент проверит себя, а вы — его. Технические детали агент выбирает сам, а время работы ни о чём не говорит.

Практика

Выберите инструмент для своей работы — из списка выше или свой — и заполните по нему шаблон ТЗ в заметках или в чате с ИИ. Оно понадобится в контрольной 6.

  • В ТЗ четыре части: что есть, что сделать, ограничения, критерии готовности.
  • Названы папки и файлы с постами, выгрузкой и правилами; названы файлы, которые появятся в репозитории.
  • В ограничениях есть все три: данные только из файлов, посты и выгрузку не менять, никуда не отправлять.
  • Критерий готовности — проверяемый пример по конкретному посту или кампании с ответом, который я знаю заранее.
  • ТЗ сохранено там, где я найду его в контрольной 6.

Вы знаете, что заказывать и как. В следующем уроке агент построит первый инструмент — проверку постов по чеклисту, — а вы примете его как заказчик.
