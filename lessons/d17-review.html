Проверить PR и оставить замечания

Агент прислал pull request с новым README. Код читать не нужно — нужно принять работу так, как вы принимаете работу помощника: сверить с первоисточником, отметить ошибки и либо утвердить, либо вернуть. Разберём на PR из урока d15.

Что вы проверяете на самом деле

Любое ревью отвечает на три вопроса: сделано ли то, что просили; не задето ли лишнее; нет ли опасного. Для PR по документам все три решаются без программирования. Результат — таблица в README, которую вы читаете как юрист; «лишнее» видно по списку тронутых файлов; «опасное» — по трём красным флагам в конце урока.

Ваше преимущество перед агентом — вы знаете, что написано в договорах. Агент видит текст, но не знает, что пустая строка с датой означает «не указано», а не «подставь дату из соседнего пункта». Поэтому в ТЗ вы написали «данные бери только из текста», а на ревью проверяете, выполнено ли это.

Как замечание дойдёт до агента

Комментарий в PR — запись для вас и коллег. Чтобы агент исправил, замечание нужно доставить туда, где он вас слышит. Это зависит от того, кто делал PR.

Вернитесь в сессию на claude.ai/code — она живёт и после создания PR — и напишите замечание в чат; текст комментария можно скопировать из PR. Агент внесёт правку новым коммитом в ту же ветку, и PR на GitHub обновится сам. Если сессия давно простаивала, она проснётся от вашего сообщения.

Откройте ту же задачу на chatgpt.com/codex, напишите замечание в ней и попросите внести правку в pull request. Новую задачу ради правки заводить не нужно — в старой уже есть весь контекст.

Облачный агент Copilot читает комментарии PR сам: оставьте замечания к строкам или общий комментарий в Conversation и ждите новых коммитов в том же PR. Это единственный из трёх агентов, с которым можно общаться, не покидая GitHub.

Три готовых запроса

Первый — когда непонятно, откуда взялись значения; второй — чтобы агент сам нашёл свои ошибки; третий — образец точечной правки.

Запрос к агенту — откуда значения
Объясни, что ты изменил в этом pull request и откуда взял каждое значение. Для каждой строки таблицы в README: файл договора и цитата из него, из которой взяты стороны, предмет, дата и срок действия. Где в договоре данных нет — так и напиши.
Запрос к агенту — самопроверка
Проверь сам свой pull request как придирчивый юрист: где ты додумал, обобщил или взял значение не из текста договора? Для каждого такого места укажи строку таблицы, что в ней написано и что в договоре на самом деле. Исправь найденное и перечисли, что исправил.
Запрос к агенту — точечная правка
Исправь только строки про договор поставки (contracts/dogovor-postavki.md): дата и срок действия должны быть дословно из текста договора; если в тексте их нет — ставь «не указано». Остальные строки таблицы и другие файлы не трогай.

Чеклист ревью

Шесть пунктов на любой PR по документам. Отмечать можно здесь — список сохраняется в браузере.

  • Ничего из contracts/ не изменено: в Files changed только файлы, разрешённые в ТЗ.
  • Данные — только из текста: стороны, даты и сроки сверены минимум по двум договорам; где в документе пусто, стоит «не указано».
  • В таблице нет ФИО, реквизитов, сумм и названий, которых не было в документах.
  • Нет внешних сервисов и отправки документов куда-либо: ни в описании PR, ни в ответах агента не упоминаются сторонние сайты и сервисы.
  • Описание PR понятное: перечислено, что прочитано и что непонятно; коллега поймёт, что изменилось.
  • Есть, как проверить: агент написал, как убедиться в результате за несколько минут, и я это сделал.

Красные флаги

Эти ситуации не обсуждаются — PR не сливается, пока агент не уберёт причину. Если настаивает — Close pull request и новое ТЗ.

  • Агент предлагает отправить документы во внешний сервис: «загрузим в онлайн-конвертер», «проверим через сторонний API». Документы не покидают репозиторий и машину агента.
  • Агент удаляет или переименовывает файлы, которых не было в ТЗ, — особенно в contracts/.
  • Агент пишет: «не смог прочитать .docx, но заполнил таблицу по названию файла». Это выдумка в аккуратной таблице. Попросите поставить библиотеку для чтения .docx и повторить — либо «не указано» по всем полям этого договора.

Проверьте себя

В Files changed кроме README.md тронут contracts/dogovor-postavki.md: агент «исправил опечатку». Что делать?

  • Слить: опечатка исправлена, это полезно
  • Слить, но написать агенту замечание на будущее
  • Не сливать: попросить вернуть договор в исходный вид — файлы в contracts/ агент не трогает

Договоры — первоисточник, их меняет только человек. Любое изменение в contracts/ — замечание до слияния, каким бы безобидным оно ни казалось.

В таблице у договора стоит дата, а в шапке договора дата не заполнена. Какое замечание верное?

  • «В шапке даты нет — поставь „не указано“. Данные только из текста договора»
  • «Проверь дату»
  • «Возьми дату из акта приёма-передачи»

Замечание должно говорить, что не так и как должно быть. Дата из другого документа — это тоже «додумал», только аккуратнее.

PR сделал Claude Code. Как доставить агенту замечание, чтобы он исправил?

  • Нажать Merge pull request — агент увидит изменения и исправит
  • Написать в чат той же сессии на claude.ai/code; правка придёт новым коммитом в тот же PR
  • Только новой задачей в новой сессии

Сессия Claude Code живёт после создания PR. Merge ничего не исправляет, а новая сессия не знает контекста старой.

В описании PR: «Файлы .docx открыть не удалось, таблица заполнена по названиям файлов». Что делать?

  • Слить: названия файлов обычно отражают содержание
  • Не сливать: данные выдуманы; попросить агента поставить библиотеку для чтения .docx и заполнить таблицу из текста или «не указано»
  • Удалить файлы .docx из репозитория

Красный флаг: правдоподобная таблица без источника. Агент умеет ставить библиотеки у себя — пусть прочитает документы по-настоящему.

Практика

Откройте PR, который агент сделал в уроке d15 или d16. Если он уже слит — не страшно: вкладка Files changed и diff у слитого PR остаются. Проведите ревью по чеклисту и отправьте агенту хотя бы одно замечание или один из трёх запросов.

  • Files changed открыт: в списке только README.md — либо лишние файлы записаны как замечание.
  • Строки таблицы сверены минимум с двумя договорами; каждое расхождение записано как замечание к строке.
  • Все шесть пунктов чеклиста ревью пройдены по этому PR.
  • Агенту отправлено хотя бы одно замечание или запрос «откуда значения» — и ответ понятен.
  • Решение принято: Merge pull request → Confirm merge → Delete branch, либо Close pull request с понятной причиной.

Вы приняли первую работу агента как заказчик. Пять минут по чеклисту закрывают основные риски. Следующий урок — что делать, когда агент сделал не то: пять сценариев и кнопка отката.
