Финальная контрольная: ваш инструмент в интернете

Без степперов, подсказок и готовых ТЗ: сделайте сами и опубликуйте второй инструмент — не тот, что в уроке 23. Это самый честный экзамен курса: вы одновременно заказчик, ревьюер и издатель. Закладывайте около часа без учёта ожидания агента.

Задание

  1. Выберите инструмент — другой, чем в уроке 23 (идеи — в таблице урока 24). Убедитесь вопросом из урока 24, что он работает без сервера: данным не нужно встречаться на двух устройствах, ничего не происходит при закрытой вкладке.
  2. Создайте новый публичный репозиторий с README и включите GitHub Pages для ветки main.
  3. Напишите ТЗ по шаблону урока 24 своими словами: поля, поведение, вывод, валидация, три контрольных примера с точными ответами. Сохраните ТЗ в репозитории — в issue или в README.
  4. Отдайте ТЗ любому агенту: Claude Code, Codex или Copilot. Дождитесь pull request и прочитайте diff.
  5. Проведите минимум две итерации с замечаниями: каждое — конкретный пример «ввёл → ожидал → получил» плюс фраза «ничего другого не меняй». Сливайте PR только после исправлений.
  6. Приведите README в порядок: что делает инструмент, для кого, как пользоваться, ограничения — чего он не учитывает.
  7. Откройте сайт с телефона и в режиме инкогнито. Проверьте на трёх примерах; один посчитайте или проверьте вручную.
  8. Напишите «защиту» из пяти предложений: что делает инструмент, кому полезен, что агент сделал плохо, как вы это исправили, что проверили. Отправьте коллеге вместе со ссылкой на сайт.

Критерии приёмки

Отмечайте только то, что проверили своими глазами. Чеклист и квиз ниже засчитывают контрольную автоматически.

  • Новый репозиторий существует, он Public, это не my-tool из урока 23; в корне лежат README.md и index.html.
  • ТЗ написано своими словами по шаблону и сохранено в репозитории — в issue или в README; в нём три контрольных примера с ответами.
  • Агент сделал минимум две итерации по моим замечаниям; замечания с примерами «ввёл → ожидал → получил» видны в истории сессии, PR или issue.
  • Я прочитал(а) diff каждого PR: только ожидаемые файлы, нет внешних скриптов и отправки данных куда-либо.
  • README отвечает на четыре вопроса: что делает инструмент, для кого, как пользоваться, что не учитывает.
  • Сайт открывается по адресу вида https://username.github.io/имя-репозитория/ в инкогнито и с телефона; форма не выезжает за экран.
  • Три контрольных примера сходятся; один я посчитал(а) или проверил(а) вручную и записал(а) в README.
  • «Защита» из пяти предложений написана и отправлена коллеге вместе со ссылкой.

Проверка понимания

Чего не хватает в запросе «Напиши письмо клиенту про задержку поставки»?

  • Вежливого обращения к ИИ и благодарности в конце
  • Контекста (кто мы, что за поставка, на сколько задержка), формата и ограничений: объём, тон, что обещать нельзя
  • Названия модели, которая должна отвечать

Без контекста и ограничений ИИ заполнит пробелы сам — и напишет общее письмо с обещаниями, которых вы не давали.

ИИ в выжимке договора пишет: «неустойка 0,5 % в день, п. 7.2». Что вы делаете перед отправкой клиенту?

  • Доверяю: ИИ читал документ целиком, а я нет
  • Спрашиваю ИИ «ты уверен?» и отправляю, если он подтвердит
  • Открываю п. 7.2 договора и сверяю цифру и единицу ставки

Модели ошибаются именно в цифрах и ссылках на пункты. «Ты уверен?» — не проверка: модель с той же лёгкостью подтвердит и ошибку.

Чем pull request отличается от коммита?

  • Коммит — сохранённый снимок изменений с подписью; PR — предложение влить ветку с коммитами в main, с diff и обсуждением до слияния
  • Это синонимы: в github.dev говорят «коммит», в Codespaces — «pull request»
  • Коммиты делает человек, а pull request может создать только ИИ-агент

Коммитов в ветке может быть много; PR объединяет их в одно предложение «принять в main», которое можно проверить, обсудить и откатить целиком.

Вы делаете калькулятор зарплат и хотите вшить в код реальную таблицу сотрудников с окладами. Почему нельзя?

  • Файл станет слишком большим для GitHub Pages
  • На бесплатном тарифе Pages работает только с публичным репозиторием — таблицу увидит кто угодно, включая поисковики
  • GitHub запрещает хранить числа в коде

Публичный репозиторий означает публичный код и всё, что в нём лежит. Данные вводятся в поля и остаются в браузере — в файл их класть нельзя.

В Claude Code вы хотите сначала увидеть план действий агента и только потом разрешить правки. Какой режим разрешений выбрать?

  • Accept edits
  • Auto
  • Plan

Plan — агент сначала предлагает план и ждёт одобрения. Accept edits меняет файлы и пушит ветку без вопросов, Auto пропускает действия через автоматический классификатор.

Что главное проверить в PR агента, если вы не программист?

  • Что код аккуратно отформатирован и в нём много комментариев
  • Что агент написал в описании PR «всё готово и протестировано»
  • Что изменения соответствуют задаче (нет лишних файлов, внешних скриптов и отправки данных) и инструмент проходит контрольные примеры

Форматирование и слова агента ничего не гарантируют. Соответствие ТЗ по diff и проверка примерами на сайте — то, что вы можете сделать сами и что реально ловит ошибки.

Если не получается

Агент сделал половину или не то

Обычно ТЗ оказалось общим: нет точных полей или примеров. Не продолжайте в том же чате. Уточните ТЗ, откройте новую сессию и начните с фразы «в репозитории уже есть index.html, доработай его, не переписывая с нуля».

Контрольный пример не сходится

Не чините код сами и не пишите «считает неправильно». Опишите агенту пример: ввод, ожидание, результат. Перед этим убедитесь, что смотрите свежую версию: PR слит, прошло до 10 минут, страница обновлена без кеша.

С телефона форма разъезжается

Это одна итерация. Замечание агенту: «на ширине экрана 360 px поля должны идти в одну колонку, кнопки — на всю ширину, текст не выходит за край экрана; остальное не трогай».

Если непонятно, где именно ошибка, — не угадывайте, спросите ИИ в обычном чате. Готовый запрос на примере калькулятора сроков:

Запрос к ИИ
Мой инструмент — одностраничный index.html на GitHub Pages: калькулятор сроков по договору, к дате прибавляет N рабочих дней (выходные — суббота и воскресенье, праздники пользователь вводит сам).
Контрольный пример не сходится: дата 13.04.2026 (понедельник), 5 рабочих дней → ожидаю 20.04.2026, инструмент показывает 17.04.2026.
Задача:
1) объясни, в чём, скорее всего, ошибка — простыми словами, без программистских терминов;
2) напиши текст замечания для ИИ-агента, чтобы он исправил только это и ничего другого не трогал;
3) предложи ещё два контрольных примера, которые поймают ту же ошибку, если она вернётся.

Поздравляем — это финал. Два инструмента в интернете, сделанных по вашему заданию, и навык, который теперь не отнять: поставить задачу, проверить, опубликовать. Остался один короткий урок — и сертификат: он появится на странице сертификата, когда все уроки отмечены пройденными.
